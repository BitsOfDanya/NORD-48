# Dynamic Connectivity Margin (satellite min-cut)

Отвечает на вопрос «сколько спутников должны отказать ОДНОВРЕМЕННО, чтобы
разорвать связь клиента со всеми доступными шлюзами прямо сейчас?» —
структурный (топологический) показатель, отдельный от вероятностных
Monte Carlo оценок и от точного N-1/N-2 перебора: та же идея «сколько
отказов выдержит сеть», но вычисленная напрямую как минимальный разрез
графа, а не перебором комбинаций.

## Алгоритм

`backend/app/calculation/resilience/connectivity_margin.py` —
`compute_connectivity_margin(graph, client_id, gateway_ids)`:

1. Узловое разбиение (node splitting): каждый узел `X` превращается в
   `X_in -> X_out` с пропускной способностью 1, если это спутник, и
   заведомо большей, чем любой возможный спутниковый разрез, если это
   наземный узел (клиент/шлюз). Это гарантирует, что минимальный разрез
   состоит ТОЛЬКО из спутников — обрезать клиента или шлюз алгоритму
   попросту невыгоднее.
2. Все доступные шлюзы сводятся в один общий сток (`sink`) — минимальный
   разрез, таким образом, разрывает связь клиента со ВСЕМИ шлюзами сразу,
   а не с одним произвольно выбранным.
3. `networkx.minimum_cut` находит минимальный разрез между клиентом и
   этим общим стоком; спутники по одну сторону разреза — это
   `critical_satellites`, размер разреза — `vertex_connectivity`.
4. Если маршрута нет изначально — `vertex_connectivity=0`,
   `critical_satellites=[]`, без попытки построить фиктивный разрез.

Детерминировано: узлы и рёбра добавляются в отсортированном порядке,
случайности в поиске максимального потока нет.

### Что НЕ означает `critical_satellites`

Если минимальных разрезов несколько, функция возвращает ОДИН из них — не
«все критические спутники сети». UI обязан формулировать это как «один
из минимальных наборов отказа», не как исчерпывающий список.

### Что НЕ означает `critical_fraction` в суточной агрегации

Суточная агрегация запускает точный расчёт на каждом шаге и считает,
как часто спутник попадал в НАЙДЕННЫЙ на этом шаге минимальный разрез.
Это частота появления в min-cut за день, а не вероятность отказа и не
абсолютная критичность спутника.

## Независимая проверка (cross-check)

Раздельно от кода, вычисляющего margin, `tests/unit/test_connectivity_margin.py`
на реальных snapshot'ах сценария `01_full_constellation`:

- при `vertex_connectivity>=2` — перебирает ВСЕ одиночные отказы спутников
  (аналог N-1) и подтверждает, что ни один не рвёт маршрут;
- при `vertex_connectivity>=3` — перебирает все 1128 пар отказов (аналог
  N-2) и подтверждает то же самое.

Оба перебора используют независимый путь кода (прямое удаление узлов +
`networkx.has_path`), не общий с `compute_connectivity_margin` — совпадение
результатов подтверждает, что min-cut алгоритм не завышает связность.

## API

В запросе нужно передать ровно один источник: `scenario_id`, полный
`scenario` или существующий `run_id`. Канонический параметр времени —
`t_s` (секунды от начала сценария); старое имя `timestamp` по-прежнему
принимается как alias (`AliasChoices`), так что уже написанные клиенты
не ломаются. Ответы описаны явными Pydantic-моделями
(`ConnectivityMarginResponse`, `DailyConnectivityResponse` +
`DailyConnectivityBucket`/`CriticalSatelliteFrequency`), а не голым
`dict[str, Any]` — FastAPI проверяет форму ответа и публикует её в
OpenAPI-схеме (см. `test_openapi_documents_critical_satellites_as_one_minimum_cut`).

### Расчёт одного timestamp

`POST /api/v1/resilience/connectivity-margin`

```json
{"scenario_id": "01_full_constellation", "client_id": "C70", "t_s": 21600}
```

Реальный ответ:

```json
{"client_id": "C70", "t_s": 21600.0, "vertex_connectivity": 2, "critical_satellites": ["S09", "S39"]}
```

### Агрегация по суткам

`POST /api/v1/resilience/connectivity-margin/daily` — тот же источник +
`client_id`, без времени: считает margin на каждом шаге всего горизонта
и агрегирует по суткам. Каждый день: `day_start_s`, `day_end_s`,
`samples_evaluated`, `minimum_vertex_connectivity`,
`mean_vertex_connectivity`, `average_when_connected` (усредняет только
значения >0, `null` если связи не было вообще), `no_route_pct` /
`margin_1_pct` / `margin_2_pct` / `margin_3_plus_pct` (доли уже
посчитанных значений в сумме дающие 100%, не новая математика),
`critical_satellites` (частоты появления в ежедневно пересчитываемом
min-cut).

Оба эндпоинта синхронные: единичный расчёт ~6-8 мс, суточный (720
снапшотов) ~1.2-2.4 с на `01_full_constellation` — заметно ниже порога,
после которого потребовался бы async job.

## UI

Встроено в `/resilience` → вкладка «Резерв маршрута»
(`components/resilience/connectivity-margin-panel.tsx`), без новой
страницы: единичная проверка (сценарий/клиент/время → степень серьёзности
текстом + список спутников минимального разреза) и суточный анализ
(минимум/среднее/среднее-при-наличии-связи + распределение в виде
горизонтальных полос, не круговой диаграммы).

## Ограничения

- `critical_satellites` — один найденный минимальный разрез, не все
  существующие при равенстве размера.
- `critical_fraction` в суточной агрегации — частота появления в
  ежедневно пересчитываемом min-cut, не оценка вероятности отказа.
- Метрика структурная (топология графа контактов на момент времени), не
  учитывает физическую наработку на отказ спутника — как и весь
  остальной расчётный слой проекта.
