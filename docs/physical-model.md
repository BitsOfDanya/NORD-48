# Физическая модель: допущения и границы

Инженерное описание того, что модель считает физически, откуда взяты
константы и что она сознательно НЕ считает — чтобы отличать «расчёт» от
«оценки на глаз». Официальная геометрия (`reference_geometry.py`,
предоставлена организаторами) не меняется этим документом и нигде в
проекте — все формулы ниже либо используют её константы напрямую, либо
описывают производные метрики поверх её результатов.

## Модель Земли и орбиты

- **Сферическая Земля**, `R = 6371.0 км` (константа `reference_geometry.R`).
- **Круговая орбита**, высота `altitude_km` (в кейсе — 550 км), заданная
  для всей группировки одним значением.
- **Гравитационный параметр** `MU = 398600.435507 км³/с²`
  (`reference_geometry.MU`) — используется без изменений в производных
  формулах ниже.
- **Вращение Земли** учитывается через `earth_angle0_deg` — начальный угол
  поворота Земли относительно инерциальной системы, дальше сдвигается
  штатной угловой скоростью вращения Земли внутри `reference_geometry.py`.
- **Наклонение** (`inclination_deg`) и распределение спутников по трём
  орбитальным плоскостям — как задано в сценарии.

## Производные орбитальные метрики (новое, `app/calculation/physics/orbital_metrics.py`)

Не меняют геометрию — читают её константы и считают дополнительные,
инженерно понятные величины поверх уже готовой модели.

- **Период обращения**: T = 2π·√(a³/μ), a = R + h. Для 550 км даёт период
  в диапазоне ~90–100 минут и ~14.5–16 оборотов/сутки — оба диапазона
  проверены unit-тестами против прямого пересчёта формулы и против
  известного порядка величины для низкой околоземной орбиты.
- **Coverage footprint** (зона покрытия одного спутника): геоцентрический
  полу-угол `psi = acos((R/(R+h))·cos(e_min)) - e_min`, откуда радиус
  зоны на поверхности (`R·psi`) и площадь сферического сегмента
  (`2πR²(1-cos(psi))`). Допущение: сферическая Земля, без учёта рельефа
  и атмосферной рефракции — то же упрощение, что уже неявно использует
  официальная модель видимости.
- **Задержка распространения**: `distance_km / c` (c = 299792.458 км/с),
  ТОЛЬКО геометрическая задержка сигнала. Не включает обработку,
  очереди, коммутацию — они нигде в проекте не моделируются, поэтому
  везде подписано «geometric propagation delay only».

## Контакт/сервис/маршрут — уже посчитанные величины, не новые

Симуляция уже считает эти поля на каждом шаге; ниже — где искать:

- **Path length** (`total_distance_km` в `RouteRecord`) — суммарная
  геометрическая длина пути клиент→...→шлюз для выбранного шага; сравнима
  между стратегиями маршрутизации (minimum_hops/minimum_distance/
  maximum_margin/maximum_persistence).
- **Route lifetime / handover metrics** (`RouteStrategyMetrics`,
  `app/calculation/routing/stability.py`) — mean/median/p05/p95/max
  route lifetime, `route_change_count`, `route_changes_per_hour` — уже
  реализовано и задокументировано в `docs/routing-experiments.md`.
- **Link margin** (`app/calculation/network/margins.py`) —
  `isl_margin(distance_km, isl_range_km)` = запас до `isl_range_km` для
  ISL-рёбер, `ground_margin(elevation_deg, min_elevation_deg)` — запас до
  порога видимости для наземных рёбер, оба нормированы в `[0,1]`. Это и
  есть «ISL range margin» / «elevation margin» — не RF link margin (см.
  ниже), а чисто геометрический запас до порога модели.
- **Contact windows / service windows**
  (`app/calculation/metrics/window_quality.py`, новое) — непрерывные
  периоды видимости (contact) и полного маршрута до шлюза (service);
  агрегация count/mean/median/p95/longest через ту же run-length логику,
  что уже использует `outage_quality.py` для перерывов (по построению,
  `total_window_s + total_outage_s == горизонт` — покрыто тестом).
- **Bottleneck decomposition**
  (`app/calculation/metrics/bottleneck_decomposition.py`, новое, уже
  подключено к `/metrics`, `/run`, `/export`) — взаимоисключающий % разбор
  причин отсутствия маршрута за весь горизонт по уже посчитанному на
  каждом шаге `diagnostic_reason` (`NO_VISIBLE_SATELLITE`,
  `NO_GATEWAY_CONTACT`, `ISL_NETWORK_SPLIT`, `GATEWAY_OUTAGE`,
  `ROUTE_AVAILABLE`). Пример реального результата: под `04_link_range`
  клиент C70 теряет 36.53% горизонта именно на `ISL_NETWORK_SPLIT`
  (для сравнения — 1.11% под штатным сценарием) — то есть просадка
  ISL2000 структурно объясняется разрывом ISL-сети, а не потерей
  видимости.

## Топология графа

Существующий `networkx`-граф контактов (`app/calculation/network/graph.py`)
уже несёт достаточно информации для агрегированных topology-метрик
(число компонент связности, размер компоненты со шлюзом, степень
спутника) — это исследовано, но НЕ подключено новым эндпоинтом в этом
проходе (см. `docs/case-acceptance.md`, раздел ограничений) — граф уже
строится один раз на шаг для routing, повторный проход по всем 720 шагам
только ради topology-статистики был признан не first-priority в рамках
текущего прохода.

## Что модель сознательно НЕ считает

- **RF link budget** — SNR, Eb/N0, capacity, RF margin: кейс не даёт
  частоту, EIRP, коэффициент усиления антенн, шум-фактор приёмника,
  полосу или схему модуляции/кодирования. Без этих входных данных любое
  число было бы придумано, а не рассчитано — поэтому таких показателей в
  проекте нет.
- **Влияние атмосферы/тропосферы на видимость** — модель видимости
  использует чистый геометрический порог по углу возвышения.
- **Задержки обработки/очередей/коммутации** — только геометрическая
  задержка распространения сигнала.
- **Деградация орбиты** (drag, радиация, топливо, срок службы) — не
  моделируется, кейс не даёт входных данных для этого.
- **Экономика запуска** (`docs/cost-sources.md`) — без введённых
  пользователем цен экономика не считается, только ресурсные объёмы
  (число спутников/запусков).
