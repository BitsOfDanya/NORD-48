# Выбор конфигурации: обоснование

Все цифры на этой странице получены точным расчётным движком
(`evaluate_configuration` / `run_n1_criticality` / `run_exact_n2`), не
оценены и не смоделированы — воспроизводимо через
`POST /api/v1/optimization/run` и `POST /api/v1/resilience/*` с указанными
параметрами. "Worst" всегда означает минимум доступности среди трёх
клиентов (C65/C70/C72) в соответствующем сценарии.

## Итоговая таблица

| Конфигурация | Normal worst | Outages worst | ISL2000 worst | N‑1 (0 нарушений) | N‑2 (0 breaking pairs) |
| --- | --- | --- | --- | --- | --- |
| Baseline (исходные RAAN/phase) | 96,67 % | 79,31 % | 62,22 % | PASS — худший S44, −2,36 п.п. | PASS — худшая пара S19+S29 → C65 91,53 % |
| Current Normal Optimum (поиск по P2/P3, budget=100) | 99,17 % | 80,28 % | 52,50 % | PASS — худший S37, −2,78 п.п. | PASS — худшая пара S37+S42 → 93,33 % |
| Denis Optimum (из `NORD48-denis`, revalidated) | 99,86 % | 81,53 % | 64,17 % | PASS — худший S15, −2,92 п.п. | PASS — худшая пара S12+S15 → 93,75 % |
| Constrained Robust Optimum (новый режим, §Constrained Robust ниже) | 98,19 % | 77,64 % | 64,17 % | PASS — худший S25, −2,78 п.п. | PASS — худшая пара S25+S26 → 92,22 % |

Все четыре конфигурации проходят N‑1 и N‑2 без единого нарушения
target ≥90 % ни на одном из 48 одиночных отказов или 1128 парных — сама
топология (48 спутников, 3 плоскости) структурно устойчива к потере 1–2
аппаратов независимо от точных углов RAAN/phase.

## Baseline

Исходные RAAN/phase из `01_full_constellation.json`. Штатный режим уже
выполняет target ≥90 % для всех клиентов (worst 96,67 %), но обе
деградированные проверки — нет: `03_satellite_outages` (79,31 %) и
особенно `04_link_range` (62,22 %, ISL ограничен до 2000 км).

## Nominal optimum (Current Normal Optimum)

Поиск (`differential_evolution`, budget=100, seed=42) только по
`P2.raan_deg/phase_deg` и `P3.raan_deg/phase_deg` (P1 зафиксирован) —
единственная цель: максимизировать штатный worst. Результат
воспроизведён точно: 96,67 % → 99,17 %, худший перерыв 480 с → 120 с.
Побочный эффект, тоже точно измеренный: оба деградированных сценария
становятся ХУЖЕ baseline — Outages 79,31 % → 80,28 % (почти не меняется),
но ISL2000 62,22 % → **52,50 %** — оптимизация "переобучилась" под
штатную геометрию и заметно ухудшила устойчивость к сокращённой
дальности ISL. Это ожидаемо: ничто в целевой функции этого режима не
защищает деградированные сценарии.

## Denis Optimum (внешняя ветка, ревалидация)

Кандидат из `../NORD48-denis` (`data/scenarios/variants/01_full_constellation_optimized.json`,
углы P1=94°/106°, P2=158°/296°, P3=27°/281°) заново точно пересчитан
ЭТИМ проектом (не взяты сохранённые метрики на веру): нормальный режим
подтверждён побайтово (99,861 % / 100 % / 100 %, как и заявлено), плюс
дополнительно проверено то, что Денис не проверял — N‑1 и N‑2 (оба PASS)
и деградированные сценарии (Outages 81,53 %, ISL2000 64,17 % — заметно
лучше nominal-оптимума по ISL2000, хотя это не было целью его поиска,
судя по большому отклонению углов от baseline, 92,75° в среднем).

## Constrained Robust Optimum — новый режим

Существовавший в проекте до этого этапа "robust"-режим
(`app/calculation/optimization/configuration.py:candidate_rank_key`)
максимизирует worst_availability **по всем сценариям вперемешку** — это
означает, что глобальный минимум почти всегда лежит в деградированном
сценарии, и штатный режим ничем не защищён. На практике это давало (по
данным, полученным до этого этапа) улучшение общего worst 62,22 % →
65,69 %, но ценой падения штатного режима до 81,25 % — недопустимо для
инженерной рекомендации, если кейс требует ≥90 % именно в штатной
работе.

Добавлен `mode="constrained_robust"` (`app/calculation/optimization/configuration.py`:
`constrained_robust_scalar`, `constrained_robust_rank_key`):

- **Ограничение**: каждый клиент в штатном сценарии обязан достичь
  target_availability. Кандидат, не удовлетворяющий этому, ВСЕГДА хуже
  любого удовлетворяющего — это гарантировано алгебраически (шкала
  разбита на два непересекающихся диапазона: `[1, ∞)` для
  недопустимых, `[0, 1)` для допустимых), а не отдельной проверкой
  после поиска.
- **Цель**: среди допустимых — максимизировать минимальную доступность
  по ВСЕМ ОСТАЛЬНЫМ (деградированным) сценариям.
- **Tie-break**: меньше худший перерыв → выше штатный worst → меньше
  отклонение параметров от baseline.

Реальный прогон (`P2/P3`, budget=150, seed=42, `01_full_constellation` +
`03_satellite_outages` + `04_link_range`): штатный режим 98,19 %
(ограничение выполнено с запасом), деградированный worst — 62,22 % →
**64,17 %** (та же цифра, что и у Денисовского кандидата — похоже, это
окрестность настоящего локального оптимума по ISL2000 при разумном
бюджете поиска). Важный честный нюанс: деградированный worst — это
минимум по ОБЪЕДИНЕНИЮ Outages и ISL2000, поэтому рост минимума не
гарантирует роста КАЖДОГО сценария по отдельности — здесь Outages worst
даже немного просел (79,31 % → 77,64 %), так как ISL2000 был связывающим
ограничением и забрал весь бюджет улучшения.

## Deployment Planner — оптимизация по этапам развёртывания

Тот же exact-поиск (budget=250, seed=42), но раздельно по трём этапам
развёртывания, оптимизируя только углы плоскостей, реально активных на
этом этапе (см. `launch_batch` в датасете: P1↔этап 1, P2↔этап 2,
P3↔этап 3):

| Этап | Аппаратов | Baseline worst | Optimized worst | Target ≥90% |
| --- | --- | --- | --- | --- |
| 1 (только P1) | 16 | 12,64 % | 14,17 % | НЕ достижимо |
| 2 (P1+P2) | 32 | 61,81 % | 69,72 % | НЕ достижимо |
| 3 (P1+P2+P3) | 48 | 96,67 % | 98,47 % | Достигнуто (уже на baseline) |

Честный вывод: на этапах 1 и 2 target 90 % физически недостижим только
подбором RAAN/phase — топология с 16 или 32 спутниками в 1–2 плоскостях
структурно не даёт достаточного покрытия/резервирования. Оптимизация
даёт измеримое, но ограниченное улучшение (+1,5 п.п. на этапе 1, +7,9
п.п. на этапе 2) — этого явно недостаточно, чтобы компенсировать
недоразвёрнутую группировку. Target становится реально достижим только
на этапе 3, где он выполняется уже без оптимизации.

## N‑1 / N‑2

Все четыре конфигурации из итоговой таблицы проверены полным точным
N‑1 (48 одиночных отказов) и точным N‑2 (все 1128 пар) — ни одна пара
или одиночный отказ не опускает ни одного клиента ниже 90 % ни в одной
из конфигураций. Это структурное свойство топологии (48 спутников, 3
плоскости, размещение шлюза), а не заслуга конкретных RAAN/phase —
устойчивость к потере 1–2 спутников не является различающим критерием
между рассмотренными кандидатами.

## Деградированная устойчивость (ISL2000)

Ограничение дальности ISL до 2000 км — самый суровый из
рассмотренных деградированных сценариев (baseline worst 62,22 % против
79,31 % у отказов 10 аппаратов). Ни одна из найденных конфигураций не
приближается к 90 % в этом сценарии одной лишь оптимизацией углов —
лучший результат (Denis / Constrained Robust) — 64,17 %, разрыв в 26
процентных пунктов. Это ожидаемо: сокращение дальности ISL — структурное
ограничение связности, а не вопрос геометрической фазировки; закрыть
такой разрыв поворотом плоскостей нереалистично без изменения
архитектуры (больше плоскостей/спутников, увеличенная дальность ISL,
доп. шлюзы).

## Рекомендация

- Если приоритет — **штатный режим**: Denis Optimum или Current Normal
  Optimum дают почти идентичный штатный worst (99,86 % vs 99,17 %), но
  Denis Optimum дополнительно НЕ ухудшает ISL2000 (64,17 % против
  52,50 % у Current Normal Optimum) — при равной штатной цели Denis
  Optimum строго лучше по Парето (не хуже по одному критерию, лучше по
  другому).
- Если приоритет — **гарантированная устойчивость при сохранении
  штатной цели**: Constrained Robust Optimum — единственный режим, где
  ограничение ≥90 % в штатном сценарии встроено в сам поиск
  алгебраически, а не проверяется постфактум. При budget=150 он достиг
  той же ISL2000-цифры, что и Denis Optimum (64,17 %), не жертвуя
  штатным режимом (98,19 % vs требуемых 90 %).
- **Неконстрейнтовый "robust"-режим** (существовавший до этого этапа)
  не рекомендуется как основной: он не даёт инженерной гарантии
  штатного target и оставлен в API только как research/advanced опция
  (см. `mode="robust"`).
- Deployment Planner показывает жёсткое физическое ограничение первых
  этапов развёртывания: пока не запущена 3‑я плоскость, target 90 %
  недостижим оптимизацией углов — планирование запуска должно это
  учитывать, а не рассчитывать на компенсацию фазировкой.
