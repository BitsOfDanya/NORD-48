# Degradation Analysis, Outage Explainability, Failover Visualization

Этап после Robust Design Search 2.0 (см. `docs/robust-design-search.md`):
отвечает не на «какая конфигурация лучше», а на «как именно она себя
ведёт при ухудшении условий, почему конкретно пропадает связь в моменте
и есть ли резервный путь». Ничего в этом документе не меняет физику,
маршрутизацию или сам поиск конфигурации — всё переиспользует
существующие точные пайплайны и добавляет только новые срезы/агрегации
поверх уже посчитанных данных.

## 1. ISL Degradation Curve (Baseline vs Recommended Robust)

Переиспользует ISL Sensitivity (`docs/isl-sensitivity.md`) без изменений
в самом sweep — фронтенд (`components/optimizer/isl-sensitivity-panel.tsx`)
опционально вызывает существующий эндпоинт `POST
/api/v1/optimization/isl-sensitivity` ДВАЖДЫ: один раз с
`scenario_id`, один раз с клиентски построенным вариантом сценария
(RAAN/phase = Recommended Robust, см. `frontend/src/lib/robust-winner.ts`
— единый источник этих чисел для всех сравнений). Backend не менялся.

Результат на `01_full_constellation`, сетка `[1800..3200]` км (16 точек) +
refine 50 км:

| Конфигурация | Требуемая дальность ISL для target ≥90% |
|---|---|
| Baseline | 2750 км |
| Recommended Robust | 2750 км |

Честный результат: фазировка НЕ снижает требуемую дальность ISL — обе
конфигурации упираются в одну и ту же границу. Это ожидаемо: Robust
Design Search 2.0 максимизировал худшую доступность при ISL=2000 км и
после 10 отказов, а не порог достижимости target в штатном режиме — это
разные целевые функции.

## 2. Failure Degradation Curve (K=0..10 отказавших спутников)

`backend/app/calculation/resilience/failure_degradation.py` — не новый
движок отказов, а оркестрация уже существующих точных инструментов:

- **K=0** — тривиально, штатный расчёт.
- **K=1** — переиспользует `run_n1_criticality` (все 48 одиночных отказов,
  исчерпывающе), берёт медиану/P10/min из уже посчитанного распределения.
- **K=2** — переиспользует `run_exact_n2` (все 1128 пар, исчерпывающе).
  Поле `pair_worst_availability_stats` считается по ПОЛНОМУ списку пар до
  усечения `worst_pairs` до топ-20 — усечение существовало только в
  отображении, не в статистике.
- **K≥3** — Monte Carlo (существующая инфраструктура
  `monte_carlo.py`), фиксированный seed для воспроизводимости.

Каждая точка помечена `method: "exact" | "monte_carlo"` — методологии не
смешиваются нигде в UI (ни в подписи графика, ни в таблице).

Async job (`failure_degradation_service.py`) — точная копия паттерна
`deployment_planner_service.py` (in-memory `_JOBS` + `threading.Lock` +
`threading.Thread`), добавлен как новые роуты в существующий
`resilience.py` (не новый файл роутера).

### Пример: `01_full_constellation`, iterations=100, seed=42

| K | Метод | Target survival · Baseline | Target survival · Robust |
|---|---|---|---|
| 0 | exact | 100% | 100% |
| 1 | exact | 100% | 100% |
| 2 | exact | 100% | 100% |
| 3 | Monte Carlo | 91,00% | 92,00% |

При K=3 Robust немного выше по вероятности сохранить target — небольшой,
но измеримый выигрыш поверх уже подтверждённых N-1/N-2 PASS.

### Закрытые пробелы точности (до, а не вместо, построения кривой)

- N-1 раньше отдавал только `worst_client_availability_drop_pp` (дельту).
  Вывод результирующей доступности из дельты был бы приближением (клиент
  с максимальным падением не обязательно становится итоговым худшим) —
  вместо этого добавлено прямое поле `worst_client_availability_percent`
  (зеркало того, что уже было у N-2).
- N-2 усекал `worst_pairs` до топ-20 — недостаточно для несмещённой
  медианы/P10 по 1128 парам. `pair_worst_availability_stats` считается по
  полному списку.

## 3. Outage Explainer

**Не LLM.** Детерминированное объяснение перерыва связи, построенное из
уже существующих категорий диагностики (`NO_VISIBLE_SATELLITE`,
`NO_GATEWAY_CONTACT`, `GATEWAY_OUTAGE`, `ISL_NETWORK_SPLIT` — см.
`app/calculation/diagnostics/diagnostics.py`, не менялся). Новых категорий
не введено — только количественные детали ЗА каждой из существующих.

### Архитектура

`backend/app/calculation/diagnostics/outage_explainer.py` —
`explain_outage(scenario, client_id, gateway_ids, t_s)`:

1. Строит ОДИН snapshot/graph на клик (по требованию, не в hot path
   `compute_timeline` — таймлайн уже общий, тяжело тестируемый код,
   трогать его для этого не нужно).
2. Переиспользует `diagnose()` за причиной.
3. Добавляет количественные детали: число видимых спутников
   (`full_graph.degree(client_id)`), ближайший к порогу спутник (из уже
   посчитанного в snapshot `elevation_deg` — для ВСЕХ активных спутников,
   не только видимых, поэтому «ближайший ниже порога» не требует новой
   геометрии), число компонент связности сети (`networkx.
   connected_components` поверх уже построенного графа), размеры
   компонент клиента/шлюза, и boolean «в одной ли они компоненте» (`None`,
   а не `False`, если компонента недоступна — не путать «не применимо» с
   «подтверждённое отличие»).

Интегрирован в СУЩЕСТВУЮЩИЙ эндпоинт: `GET
/api/v1/simulations/{run_id}/route` теперь добавляет поле `"explanation"`
в ответ, ТОЛЬКО когда `available=false`. Новых эндпоинтов не создано.

### UI

`frontend/src/lib/outage-intervals.ts` — чисто клиентская группировка
последовательных недоступных шагов таймлайна (уже загруженного через
`/timeline`) в интервал `{start_s, end_s, duration_s, representative_t_s}`
(представительная точка — середина интервала, детерминированный выбор).

`components/network/outage-explainer.tsx`, встроен в
`components/network/route-panel.tsx`: кнопка «Почему нет связи?» → на
клик единственный запрос `/route` в представительной точке интервала →
короткий текстовый ответ → раскрываемые «Подробности графа».

### Пример (реальный, `04_link_range`, клиент C65, t=01:50)

```
C65, 01:50–01:52, Перерыв: 2 мин
Причина: Разрыв межспутниковой сети
Видимых спутников: 1
Контакт со шлюзом: есть
Сеть разделена: 37 компонент
Клиент и шлюз находятся в разных компонентах
Размер компоненты клиента: 10, размер компоненты шлюза: 2
```

И для `NO_VISIBLE_SATELLITE` (тот же сценарий, t=16:30):

```
Видимых спутников: 0
Порог угла места: 10.0°
Ближайший к порогу: S48 (9.5°)
```

## 4. Recovery Analysis (Baseline vs Robust)

`backend/app/calculation/optimization/robust_explainability.py` уже
существовал (написан для объяснимости поиска), но не был подключён ни к
одному API — это единственная часть этапа, где пришлось добавить
недостающий мост, а не только новый эндпоинт поверх готовой функции.

`compute_recovery_stats(baseline_timeline, candidate_timeline, step_s)` —
по каждому клиенту считает шаги, где baseline не имел маршрута, а
candidate имеет («recovered»), и ЧЕСТНО — обратные случаи, где candidate
теряет связь там, где baseline её имел («lost», регрессия). Ничего не
скрывается: обе цифры показываются рядом.

### API

`POST /api/v1/comparisons/recovery` — новое расширение СУЩЕСТВУЮЩЕГО
роутера `comparisons.py` (не новый файл): принимает `baseline_run_id` +
`candidate_run_id` двух уже завершённых прогонов (`/simulations/run`,
тот же паттерн, что и обычный Compare), возвращает `per_client`,
`summary` (recovered/lost/net в секундах), `dominant_recovery_reason`,
и по одному детерминированному примеру `recovered_example`/
`lost_example` (самый ранний по client_id, затем по времени переход —
не «самый интересный», а воспроизводимый).

### UI

`components/comparison/recovery-comparison.tsx`, встроен в
`ComparisonWorkspace` (`/compare`) — для каждого не-baseline варианта в
текущем сравнении. Показывает Recovered/Lost/Net одной строкой, таблицу
по клиентам, и оба примера с путём кандидата/baseline. **Ни один сегмент
пути НЕ называется «критическим»** — это требует формального
min-cut/connectivity-margin анализа (зона другого участника проекта),
здесь используется нейтральная формулировка «связь, присутствующая в
конфигурации».

## 5. Primary + Backup Route Visualization

Переиспользует логику Route Redundancy (`docs/network-redundancy.md`,
`app/calculation/resilience/redundancy.py`) — тот же тест «удалить
промежуточные узлы основного пути, попробовать найти маршрут снова», но
для ОДНОГО клика (client, t_s) вместо агрегации по всему горизонту.

`find_backup_path(scenario, client_id, gateway_ids, t_s, primary_path)` —
новая функция в том же модуле, не новый алгоритм. Поиск резерва всегда
идёт по minimum-hops связности независимо от стратегии основного
маршрута — пересчитывать persistence-aware резерв означало бы
перестраивать весь горизонт заново на каждый клик, что противоречит
принципу «дёшево и по требованию».

Подключено к СУЩЕСТВУЮЩЕМУ эндпоинту `GET .../route`: при
`available=true` в ответ добавляется `backup_path` (список узлов или
`null`, если независимого резерва нет).

### UI

`components/network/backup-route-panel.tsx` (кнопка «Показать резервный
маршрут», по требованию — не в hot path). На глобусе
(`globe-canvas.tsx`): основной маршрут — существующий цвет
(`#f2c14e`), резервный — приглушённый янтарный
(`rgba(197, 148, 74, 0.55)`, тоньше линией). Легенда «Резервный маршрут»
показывается ТОЛЬКО когда резерв действительно найден.

### Failure Lab: reroute / explanation

Существующий Failure Lab (`docs/failure-analysis.md`) уже считает полный
`RouteRecord` (включая `path`, `diagnostic_reason`) для сценария с
отказавшими спутниками — просто не выставлял эти поля наружу.
Добавлены `failed_path`/`failed_reason` в уже существующий
`timeline_impact` (чисто аддитивно, без нового вычисления). Клик по
полосе FAILURE в `components/resilience/failure-lab.tsx` показывает:

- связь сохранена → **«Маршрут перестроен»** (если путь изменился) или
  «маршрут не изменился», плюс сам путь;
- связи нет → «Связь отсутствует» + причина (`diagnostic_reason`, без
  выдумывания новой категории).

Без анимации переключения — только состояния «до» (панель клиента) и
«после» (эта карточка).

## 6. Summary: «Поведение при деградации»

`components/summary/robust-design-highlight.tsx` расширен (не
переделан) четырьмя новыми числами (Normal/Outages/ISL2000 worst, Backup
path mean) и компактным блоком с порогами ISL и K=3 survival

без обещания target 90% при ISL=2000 км (его нет ни у одной
конфигурации).

## Ограничения

- Backup-path поиск при клике — по minimum-hops, не по стратегии
  основного маршрута (см. раздел 5) — сознательное упрощение.
- Recovery/Backup вычисления — по требованию (клик), не встроены в
  hot path `compute_timeline`/snapshot polling — специально, чтобы не
  замедлить обычный просмотр таймлайна.
- Failure degradation при K≥3 — оценка Monte Carlo с фиксированным
  seed, не исчерпывающий перебор (число комбинаций растёт
  комбинаторно) — не путать точность метода с точностью K=0..2.
- Ни один участок маршрута не помечен «критическим» — это осталось
  зоной формального min-cut/connectivity-margin анализа.
- Всё содержимое этого этапа не трогает `reference_geometry.py`,
  маршрутизацию, deployment planner, ML/surrogate-модель.
