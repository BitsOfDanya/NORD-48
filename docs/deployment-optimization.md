# Hybrid Deployment Optimization

Соединяет два уже существующих, по отдельности проверенных инструмента в
один сквозной pipeline — без нового алгоритма поиска, только оркестрация:

```
1. Subset selection      →  greedy_sequence() / verify_threshold()
2. RAAN/phase refinement →  refine_stage() (тот же search.optimize(), что и /optimizer)
3. Exact revalidation    →  evaluate_subset() на финальной конфигурации
```

Каждый шаг переиспользует существующий, отдельно протестированный код
(`backend/app/calculation/optimization/deployment_planner.py`); ничего в
`reference_geometry.py` не менялось для реализации ни одного из шагов.

## Шаг 1 — состав (какие именно спутники)

`greedy_sequence()` — жадный конструктивный поиск (см.
docs/deployment-planner.md для алгоритма и тай-брейка). Результат — список
`SubsetEvaluation`, по одному на каждый размер `1..max_size`.

## Шаг 2 — геометрия (RAAN/phase для уже выбранного состава)

`refine_stage()` фиксирует состав, выбранный на шаге 1, и запускает ТОТ ЖЕ
exact-оптимизатор, что и вкладка «Поиск RAAN/phase» — просто область
поиска сужена до уже выбранного подмножества спутников как единственного
профиля. Возвращает `derived_scenario` — сценарий с уточнёнными углами,
готовый открыть в моделировании одной кнопкой.

## Шаг 3 — точная ревалидация

Финальная конфигурация (состав + уточнённая геометрия) пересчитывается тем
же exact-пайплайном (`evaluate_subset`/`evaluate_configuration`), что и
шаги 1-2 — не отдельной, потенциально рассинхронизированной метрикой.
Никаких «предполагаемых» чисел, только то, что реально посчитано.

## Nested Deployment Sequence (Stage1 ⊂ Stage2 ⊂ Stage3)

Важное свойство, которое НЕ потребовало отдельного алгоритма: поскольку
`greedy_sequence()` строит ОДНО непрерывное, монотонно растущее множество
(на каждом шаге добавляется спутник к уже выбранным, ничего не
убирается), любые под-множества размера 16/32/48, взятые из ОДНОЙ И ТОЙ ЖЕ
последовательности, автоматически вложены друг в друга по построению:

```
Stage1 (N=16) ⊂ Stage2 (N=32) ⊂ Stage3 (N=48)
```

Это значит, что развёртывание в реальности МОЖНО выполнить поэтапно:
запустить состав Stage1, затем ДОБАВИТЬ спутников до состава Stage2, не
меняя уже запущенные — то, что жадный алгоритм выбрал для Stage1, никогда
не выводится из группировки на Stage2/Stage3. Никакого отдельного
«nested planner» строить не нужно — это готовое свойство инкрементального
построения. (Если бы состав для каждого N выбирался НЕЗАВИСИМО — например,
отдельным поиском под каждый размер — вложенность НЕ гарантировалась бы;
именно поэтому planner использует одну последовательность, а не N
отдельных поисков.)

## Nested sequence под геометрией Recommended Robust 2.0 (не baseline-углы)

Более ранний прогон этого раздела (следующая секция) использовал
DEFAULT/baseline RAAN/phase сценария — те же углы, которые всё равно не
летят, потому что финальная рекомендация — Robust 2.0. `plane_parameters`
в `DeploymentPlanRequest` позволяет зафиксировать ЛЮБУЮ геометрию (в
частности — уже верифицированный Robust 2.0) и искать состав Stage1/2
именно под неё, не трогая саму геометрию.

Exact greedy sweep (`minimum_hops`, полный проход 1..48, 267.4с) под
Robust 2.0 углами:

| Этап | Reference (launch_batch≤stage) | Optimized (жадный состав) | Прирост |
| --- | --- | --- | --- |
| Stage 1 (N=16) | 13,19 % (P1:16/P2:0/P3:0) | **32,22 %** (P1:5/P2:5/P3:6) | ×2,4 |
| Stage 2 (N=32) | 56,53 % (P1:16/P2:16/P3:0) | **65,56 %** (P1:9/P2:11/P3:12) | +9,03 п.п. |
| Stage 3 (N=48) | 96,53 % | 96,53 % (= Robust 2.0, все спутники активны) | — |

Backup mean по стадиям (Optimized): Stage1 4,31% → Stage2 12,41% →
Stage3 30,05%. Connectivity margin (mean vertex connectivity) растёт
монотонно: Stage1 ≈0,35-0,38 → Stage2 ≈0,74-0,82 → Stage3 ≈1,17-1,39.
«Прирост за запуск» (delta worst availability): Stage1 +32,22 п.п.,
Stage2 +33,33 п.п., Stage3 +30,97 п.п. — примерно равномерный вклад
каждого этапа запуска, не убывающая отдача.

Вывод не меняет Recommended (Robust 2.0 остаётся финальной геометрией) —
это ответ на отдельный инженерный вопрос «в каком порядке выводить уже
выбранные 48 спутников», не альтернатива финальной конфигурации.

## API

`POST /api/v1/optimization/deployment-plan/run` — `DeploymentPlanRequest`
(`stage_sizes`, `refine_budget`, `refine_seed`, `max_search_size`,
`plane_parameters` — опциональный override RAAN/phase, например Robust
2.0, применяется ДО поиска состава) — общий job-эндпоинт, полностью
покрывающий все три шага за один запуск. Каждый `stage_sizes` элемент
проходит шаги 1-3 (шаг 2 — только если `refine_budget > 0`).

## End-to-end проверка (шаг 2, реальный контролируемый прогон)

Оркестрация subset → refine → revalidation запущена вживую на реальных
жадных составах, не только протестирована юнит-тестами:

| Состав | Budget | Baseline worst | После refine | Δ |
| --- | --- | --- | --- | --- |
| Stage 1 (N=16, жадный) | 30 | 31,39 % | 31,39 % | 0 |
| Stage 1 (N=16, жадный) | 150, seed=7 | 31,39 % | 31,39 % | 0 |
| Stage 2 (N=32, жадный) | 30 | 64,31 % | 64,31 % | 0 |
| N=44 (после swap-refinement) | 60 | 90,14 % | 90,14 % | 0 |

**Честный результат: улучшения не найдено ни на одном из четырёх
прогонов** (включая 5-кратно увеличенный бюджет и другой seed для
Stage 1) — `best.parameters == baseline.parameters` побайтово, то есть
search реально перебирал пространство (это не отказ поиска стартовать),
просто ни один кандидат не превзошёл стартовую точку. Правдоподобное
объяснение: жадный алгоритм выбора состава (docs/deployment-planner.md)
УЖЕ распределяет спутники равномерно по всем плоскостям при заданных
(немодифицируемых) базовых RAAN/phase — в отличие от наивного
покомпонентного состава `02_first_launch` (вся Stage 1 — одна плоскость
целиком), где refine ранее находил измеримое улучшение (12,64% → 14,17%,
см. docs/deployment-planner.md). Для СОСТАВА, уже подобранного жадным
алгоритмом с учётом текущей геометрии, дальнейшее вращение плоскостей
целиком, по-видимому, не даёт выигрыша — жадный выбор состава и
RAAN/phase-геометрия конкурируют за одну и ту же степень свободы
(«где физически размещены рабочие спутники»), а не дополняют друг друга.

Это не означает, что оркестрация не нужна — для ДРУГИХ (не
жадно-оптимизированных) составов эффект уже показан в
docs/deployment-planner.md. Она означает: для конкретных жадных
кандидатов этой сессии (Stage 1/2 и N=44) второй шаг не улучшил результат
— зафиксировано честно, а не подставлено произвольное число.

## Ограничения

- Шаг 1 — эвристика (см. docs/deployment-planner.md и
  docs/design-threshold-verification.md про независимую проверку);
  результат шага 2 зависит от бюджета RAAN/phase-поиска, переданного в
  `refine_budget` — маленький бюджет может не найти лучшую геометрию.
- Вложенность гарантирована ТОЛЬКО для составов из одной последовательности
  `greedy_sequence()` при одинаковых scenario/routing_strategy — сравнение
  с посторонним, отдельно оптимизированным составом такого свойства не
  имеет.
