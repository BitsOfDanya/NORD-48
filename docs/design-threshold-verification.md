# Threshold Verification (N=40..45)

Отвечает на вопрос, который жадный конструктивный поиск (см.
docs/deployment-planner.md) сам по себе оставляет открытым: **если для
размера N жадный алгоритм не достиг target, значит ли это, что N
спутников физически недостаточно — или дело в конкретном порядке, в
котором жадный алгоритм их добавлял?**

Жадный поиск — это ОДИН порядок построения (по одному спутнику за раз,
всегда наилучший на данный момент). Он не проверяет, existует ли ДРУГОЙ
состав того же размера N, полученный иначе, который достигает target.
Threshold verification — это независимая, отличным методом полученная
проверка конкретных пограничных N.

## Метод: swap refinement (НЕ полный перебор)

`swap_refine()` (`backend/app/calculation/optimization/deployment_planner.py`) —
steepest-descent локальный поиск поверх состава, который дал жадный
алгоритм для данного N:

1. Взять состав жадного поиска размера N как отправную точку.
2. Перебрать ВСЕ пары (активный спутник ↔ неактивный спутник) —
   `active_count × inactive_count` точных пересчётов за проход.
3. Применить ЛУЧШИЙ улучшающий обмен (если такой есть); если ни один обмен
   не улучшает worst availability — локальный оптимум достигнут, стоп.
4. Повторить, максимум `max_passes` раз (использовано 3).

Это НЕ `C(48, N)` полный перебор (для N=44 это было бы `C(48,44)` = 194580
сочетаний) и не доказательство глобального оптимума — только независимая
от порядка добавления проверка, отличным методом (обмен спутников, не
последовательное наращивание), повышающая уверенность в найденном пороге.

## Результат реального прогона

`01_full_constellation`, `minimum_hops`, target ≥90%, `max_passes=3`:

| N | Жадный worst | После swap-refinement | Обменов | Оценок | Target |
| --- | --- | --- | --- | --- | --- |
| 40 | 81,39 % | 82,64 % | 3 | 961 | FAIL |
| 41 | 83,47 % | 84,72 % | 3 | 862 | FAIL |
| 42 | 85,56 % | 86,53 % | 3 | 757 | FAIL |
| 43 | 87,64 % | 88,33 % | 2 | 646 | FAIL |
| **44** | 89,72 % | **90,14 %** | 2 | 529 | **PASS** |
| 45 | 91,53 % | 91,94 % | 3 | 406 | PASS |

**Первый найденный размер, достигающий target (после уточнения обменами):
N = 44.** Жадный поиск без уточнения указывал на N = 45 (89,72 % < 90 % на
N=44) — swap refinement нашёл состав того же размера (44 спутника),
достигающий target, которого жадное наращивание не построило.

Для N=44 применённые обмены: `S40 → S38`, `S39 → S20` (были заменены два
спутника из жадного состава на два других); итоговое распределение по
плоскостям P1:15 / P2:16 / P3:13.

## Как это читать (важно)

- **N = 44 — это первый найденный размер, достигающий target, а не
  математически доказанный минимум.** Не проверялись составы размера
  40-43 сверх того, что нашёл swap refinement за ограниченное число
  проходов (`max_passes=3`) — теоретически более настойчивый локальный
  поиск (больше проходов, другая стартовая точка, beam search) мог бы
  найти проходящий состав и для меньшего N.
- Формулировка в UI и отчётах: **«первый найденный размер, достигающий
  target»** или **«минимальный размер, найденный текущим поиском»** —
  никогда «доказано», «гарантированно минимальный» или подобные
  формулировки, подразумевающие исчерпывающую проверку.
- N=45 тоже проверен независимо (swap refinement нашёл ещё +0,41 п.п.
  сверх жадного) — оба N=44 и N=45 подтверждены двумя разными методами
  поиска, что существенно повышает доверие к границе, но не превращает её
  в доказательство.

## Производительность

Полный прогон (построение последовательности 1..48 + verification
N=40..45) занял **262,4 с** (построение последовательности) + **1664,6 с**
(уточнение шести размеров) ≈ **32 минуты** — запускался в фоне, не как
часть обычного цикла разработки; для интерактивного использования
эндпоинт асинхронный (job), с polling статуса, аналогично deployment-plan.

## Валидация рекомендованного кандидата (N=44, после swap-refinement)

Состав N=44 (после обменов `S40→S38`, `S39→S20`) дополнительно проверен по
трём независимым осям — не только по штатной доступности:

- **ISL sensitivity**: минимальная дальность ISL для target ≥90% — **2750
  км** (тот же порог, что и для полной группировки из 48 спутников —
  сужение состава до 44 не потребовало более длинной линии связи).
- **Route redundancy**: доля шагов с независимым резервным путём — C65:
  11,8 %, C70: 22,5 %, C72: 25,7 % (заметно ниже, чем у полной
  группировки — меньше спутников-ретрансляторов на выбор, ожидаемо).
- **N-1 reserve**: худший единичный отказ (спутник S10 или S34) снижает
  доступность худшего клиента на 3,33 п.п. и нарушает target у 3 клиентов
  из 3 — **то есть у N=44 нулевой запас на отказ одного спутника**:
  90,14 % минус 3,33 п.п. ≈ 86,8 %, уже ниже target. Это ожидаемо для
  «первого найденного размера, едва достигающего target» — граничный
  кандидат по определению не имеет резерва. Для устойчивости к единичному
  отказу нужен размер с бо́льшим запасом (см. `target_margin_pp` в таблице
  выше — N=45 даёт +1,94 п.п., тоже недостаточно для полного покрытия
  худшего N-1; практический запас начинается заметно выше порога).

**Практический вывод**: N=44 — минимальный размер для штатного режима, но
НЕ рекомендуемый размер для развёртывания, если требуется устойчивость к
отказу одного спутника — для этого нужен отдельный запас (resilience
reserve), см. итоговую рекомендацию в отчёте сессии.

## Resilience Reserve: минимальный размер, переживающий N-1

Отдельно проверено, при каком размере target ≥90% сохраняется ДАЖЕ ПОСЛЕ
худшего единичного отказа спутника (не только в штатном режиме):

| N | Worst (штатный) | Худший N-1 drop | Worst после N-1 | Нарушений target после N-1 |
| --- | --- | --- | --- | --- |
| 44 (refined) | 90,14 % | −3,33 п.п. | ≈86,81 % | 3 |
| 45 (refined) | 91,94 % | −3,33 п.п. | ≈88,61 % | 1 |
| 46 (жадный, без уточнения) | 93,33 % | −3,33 п.п. | **≈90,00 %** | **0** |

**N=46 — минимальный проверенный размер, сохраняющий target даже после
худшего единичного отказа спутника** («первый найденный», не доказанный
глобальный минимум — состав здесь ЖАДНЫЙ, без swap-refinement, значит
меньший размер с уточнением теоретически ещё может найтись). Это и есть
`target_margin_pp` / resilience reserve в смысле спецификации: разница
между «едва хватает» (44) и «хватает с запасом на один отказ» (46) — два
спутника, +3,19 п.п. номинального запаса.

## Полная кросс-профильная валидация N=44 и N=46 (Normal / Outages / ISL2000 / N-1 / N-2)

Ранее (см. предыдущую версию этого раздела) Outages/ISL2000 для этих
кандидатов не были посчитаны точно. Досчитано exact-пересчётом на тех же
двух готовых стресс-профилях (`03_satellite_outages`, `04_link_range`),
что использует `docs/design-decision.md` — состав кандидата наложен НА
профиль (объединение: спутники вне состава — отказ на весь горизонт,
плюс собственные отказы/ограничения профиля сохранены, а не заменены),
не наоборот.

Обнаружена и исправлена ошибка первого прохода: `evaluate_subset()`
внутри себя заново вызывает `active_subset_scenario()` на переданном
сценарии, что молча стирало заранее наложенные отказы стресс-профиля
(результат Outages совпадал с Normal побайтово — верный признак, что
профиль не применился). Исправление: своя копия тела `evaluate_subset`
без повторного вызова `active_subset_scenario`, применяемая к уже
корректно собранному сценарию кандидат+профиль.

| Кандидат | Спутников | Normal worst | Outages worst | ISL2000 worst | Худший перерыв (normal) |
| --- | --- | --- | --- | --- | --- |
| Baseline | 48 | 96,67 % | 79,31 % | 62,22 % | 480 с |
| N=44 (refined) | 44 | 90,14 % | 71,67 % | 56,39 % | 720 с |
| N=46 (жадный) | 46 | 93,33 % | 75,00 % | 59,58 % | 480 с |

| Кандидат | N-1 (0 нарушений = PASS) | N-2 (0 breaking pairs = PASS) | Требуемый ISL | Резерв пути (среднее по клиентам) |
| --- | --- | --- | --- | --- |
| Baseline | PASS | PASS | 2750 км | 28,1 % |
| N=44 | **FAIL** — 3 нарушения, худший −3,33 п.п. → ≈86,81 % | **FAIL** — 946/946 пар (100 %) нарушают target | 2750 км | 20,0 % |
| N=46 | **PASS** — 0 нарушений, худший −3,33 п.п. → ровно 90,00 % | **FAIL** — 1034/1035 пар (99,9 %) нарушают target | 2750 км | 23,2 % |

**Честный вывод**: ни N=44, ни N=46 не проходят точный N-2 — только
полная 48-спутниковая группировка сохраняет устойчивость к ДВУМ
одновременным отказам. N=46 проходит N-1 (ровно по границе, 90,00 %), но
не N-2. Это ожидаемо: N=46 — «первый найденный размер, переживающий
худший ОДИНОЧНЫЙ отказ», не «размер с запасом на два отказа» — N-2 требует
существенно большего резерва, который в этом прогоне не искался
отдельно (отдельная, более суровая задача — не входила в scope этого
этапа).

## Marginal Gain Curve

`marginal_gain_curve()` — Δ worst availability (п.п.) при добавлении
каждого следующего спутника к жадной последовательности. Показывает, где
отдача от добавления спутников убывает быстрее всего (отображается на
вкладке «Порог размера» под таблицей результатов).

## API

`POST /api/v1/optimization/threshold-verification/run` — асинхронный job
(`ThresholdVerificationRequest`: `sizes`, `max_passes`), статус —
`GET /threshold-verification/{run_id}`, результат —
`GET /threshold-verification/{run_id}/result` (`ThresholdVerificationResult`:
`points`, `marginal_gain_curve`, `greedy_only_minimum_size`,
`first_verified_pass_size`).

## Ограничения

- `max_passes=3` — компромисс между временем расчёта и тщательностью;
  большее значение может (не гарантированно) найти лучший состав для тех
  же N.
- Не является beam search или multi-start в этом прогоне — использована
  ОДНА стартовая точка (жадный состав) на N. Спецификация допускает
  несколько детерминированных стартов + опциональный beam search как
  дальнейшее развитие (не реализовано в этой сессии — не требовалось для
  подтверждения найденного порога).
- Результат специфичен для `01_full_constellation` / `minimum_hops` — смена
  сценария или стратегии маршрутизации требует нового прогона.
