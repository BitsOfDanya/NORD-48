# Эксперименты маршрутизации

## Методика

Для каждого из четырёх исходных сценариев выполнен детерминированный прогон всех
720 snapshot с шагом 120 с для `minimum_hops`, `minimum_distance`,
`maximum_margin` и `maximum_persistence`. Геометрия и контакты взяты из
неизменённого `reference_geometry.py`. Случайного sampling и ML нет.

Lifetime в сводных таблицах считается по **фактически выбранным route segments**:
непрерывным периодам, на которых выбранный путь не меняется. Это не то же самое,
что instantaneous lifetime в ответе route: последнее отвечает на вопрос «сколько
проживёт выбранный сейчас путь, если его не перестраивать». Margin и hops
агрегируются по доступным snapshot. `route_change_count` равен числу новых
доступных сегментов после первого; outage завершает сегмент.

## Метрики

- `availability` — прежняя доля snapshot, где существует путь к шлюзу;
- `median/P05 lifetime` — статистика длительности route segments;
- `mean/P05 margin` — статистика запаса слабейшей линии выбранного пути;
- `changes` — число перестроений за сутки;
- `mean hops` — среднее число рёбер доступного пути.

В таблицах availability и margin указаны в процентах, lifetime — в секундах.

## Наблюдения

1. Availability совпадает у всех стратегий во всех 12 комбинациях сценарий ×
   клиент. Это ожидаемо: стратегии выбирают разные пути в одном связном графе.
2. `maximum_margin` действительно даёт лучший mean margin во всех комбинациях и
   обычно лучший P05 margin, но платит дополнительными hops и частыми сменами.
3. Гипотеза, что `maximum_margin` также продлевает route segments, не
   подтверждается: медиана не выше ни в одной комбинации и в нескольких ниже.
4. `maximum_persistence` максимизирует instantaneous lifetime при каждом новом
   выборе, однако независимый пересчёт на каждом snapshot может переключиться на
   новый путь с более далёким expiry ещё до разрыва текущего. Поэтому segment
   lifetime и churn не обязаны быть глобально лучшими. Это важное ограничение
   stateless routing policy, а не ошибка exact search.

Контроль `04_link_range / C70 / t=21600`:

| Стратегия | Путь | Hops | Margin | Instantaneous lifetime |
| --- | --- | ---: | ---: | ---: |
| minimum_hops | C70 → S09 → G_MUR | 2 | 1,1385 % | 360 с |
| maximum_margin | C70 → S25 → S09 → G_MUR | 3 | 1,6032 % | 120 с |
| maximum_persistence | C70 → S09 → G_MUR | 2 | 1,1385 % | 360 с |

Числа 1,14 % и 1,60 % воспроизведены. Более высокий запас в этой точке не
означает более долгую жизнь: путь `maximum_margin` исчезает на следующем шаге.

## Рекомендация

API применяет заданный лексикографический порядок к средним по трём клиентам:
availability → median segment lifetime → P05 margin → меньше changes → меньше
hops. Фактические рекомендации: `minimum_distance` для full constellation,
satellite outages и ISL 2000; `maximum_persistence` для first launch. Это не
универсальное превосходство: для максимизации запаса выбирается
`maximum_margin`, а для минимизации числа переходов — `minimum_hops`.

## Ограничения

- Дискретизация 120 с: разрыв внутри интервала локализуется только следующим
  snapshot.
- Stateless пересчёт маршрута на каждом snapshot не включает hysteresis или
  стоимость переключения; это отдельная возможная стратегия.
- Последний живой путь цензурирован правой границей суток: его lifetime известен
  только до конца доступного горизонта.
- Полученный dataset может позже использоваться для surrogate optimization
  конфигурации `RAAN/phase → качество`, но ML не нужен и не используется для
  поиска пути в графе из 48 спутников.
