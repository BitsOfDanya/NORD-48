# Route Redundancy (резервирование маршрутов)

Отвечает на вопрос, который «есть ли маршрут вообще» не задаёт: **если у
клиента ЕСТЬ маршрут прямо сейчас, есть ли у него независимый запасной,
или он держится на одной-единственной цепочке спутников?** Две
конфигурации могут иметь одинаковую доступность (сколько времени связь
вообще есть), но радикально отличаться по тому, насколько один отказ
способен эту связь оборвать.

## Алгоритм

Для каждого клиента и каждого шага времени, на котором маршрут найден
(`backend/app/calculation/resilience/redundancy.py`, `compute_redundancy`):

1. Строится маршрут обычным способом (`compute_route`, та же логика, что
   и в основной симуляции — ничего не меняется в маршрутизации).
2. Если маршрут прямой (клиент — шлюз без ретрансляторов), резервный путь
   структурно негде проверять — это учитывается отдельно как
   `single_path` (нет промежуточных узлов, которые можно было бы убрать).
3. Иначе промежуточные спутники основного пути удаляются из графа ЭТОГО
   шага (копия графа, исходные данные не мутируются — см.
   `test_source_graph_not_mutated`), и маршрут ищется заново.
4. Если второй маршрут найден — это независимый резерв (`backup`); не
   найден — клиент зависел от единственной цепочки (`single`).

Три результата на клиента, **не единая свёрнутая метрика**:

```
no_route_percent + single_path_percent + backup_path_percent = 100
```

## Почему не единый «score»

Смешивание «есть резерв» и «резерва нет, но путь всё равно есть» в одно
число (например, 0.5 за «частичную» устойчивость) скрыло бы главный
инженерный факт: клиент либо переживёт единичный отказ спутника на пути,
либо нет. Три раздельных процента дают это без интерпретации.

## Стоимость расчёта

Полный проход почти вдвое дороже обычной симуляции (каждый шаг с
маршрутом требует второго поиска пути после удаления узлов) — метрика
считается по требованию (`POST /api/v1/resilience/redundancy`), не как
часть каждой обычной симуляции.

## API и хранение состояния

`POST /api/v1/resilience/redundancy` — `RedundancyRequest`
(`scenario_id` или `scenario`, `routing_strategy`) → `RedundancyResult`
(`clients: Record<client_id, ClientRedundancyStats>`). Результат хранится
в сторе как `resilienceResults.redundancy` — переживает переключение
вкладок и перезагрузку страницы, как и остальные результаты Resilience
(см. docs/persistence.md).

## Ограничения

- Определение «независимости» — только по совпадению использованных
  спутников-ретрансляторов на данном шаге; наземная инфраструктура (шлюз)
  не варьируется — если единственный доступный шлюз недоступен, ни один
  анализ резервирования путей это не покажет (это отдельная метрика —
  доступность конкретного шлюза).
- Метрика не учитывает ВРЕМЯ переключения между основным и резервным
  путём (задержка на решоминг маршрута) — просто "существует ли
  альтернатива в тот же момент времени", не "как быстро на неё
  переключиться".
- Считается независимо для каждого шага — не проверяет, остаётся ли ОДИН
  И ТОТ ЖЕ резервный путь стабильным на протяжении нескольких шагов
  подряд (это ближе к метрике route churn / route stability, уже
  посчитанной отдельно, см. docs/routing-experiments.md).
