# Deployment Sequence Planner

Отвечает не на «что даёт готовый сценарий `02_first_launch`», а на другой,
более полезный инженерный вопрос: **если бы можно было выбирать, какие
именно N аппаратов запускать первыми, какой состав дал бы лучший
результат** — и насколько это отличается от «наивного» состава (все
спутники одной плоскости, как в `02_first_launch`/`design.launch_stage`).

## Почему не перебор всех сочетаний

Выбор лучших N спутников из 48 — это `C(48, N)` сочетаний: для N=24 это
≈10¹³, физически невозможно перебрать точным расчётом (каждый вариант —
полная 720-шаговая симуляция). Полноценный локальный поиск (simulated
annealing, генетический алгоритм) был бы более тщательным, но неоправданно
сложным для этой задачи: добавление ретранслятора почти всегда только
добавляет пути связности, не убирает — то есть задача близка к
монотонному покрытию, для которого **жадный конструктивный алгоритм**
(«на каждом шаге добавить того единственного спутника, который сильнее
всего улучшает худшего клиента прямо сейчас») даёт результат, очень
близкий к истинному оптимуму, ценой `O(n²)` точных расчётов (для n=48 —
1128 расчётов) вместо астрономического числа сочетаний.

**Это эвристика, не доказательство оптимальности** — если для какого-то N
существует лучший состав, жадный алгоритм его не гарантированно найдёт.
Он детерминированный (без случайности: голые числа RNG нигде не участвуют)
и полностью воспроизводимый — при одинаковых входных данных всегда даёт
одинаковый результат (см. `test_greedy_sequence_is_deterministic`).

## Алгоритм

Один проход, вложенный по построению:

1. Шаг 1: перебрать все 48 кандидатов, точно посчитать доступность для
   каждого как единственного активного спутника, выбрать лучшего.
2. Шаг k: к уже выбранным `k-1` спутникам поочерёдно добавляется каждый
   из оставшихся кандидатов, для каждого варианта — полный точный расчёт
   (720 шагов), выбирается лучший по критерию (см. ниже).
3. Повторять, пока не выбраны все 48 (или пока не достигнут `max_size`).

Активность произвольного подмножества спутников реализована БЕЗ изменения
`launch_batch`/`launch_stage` семантики и без правки `reference_geometry.py`:
спутники НЕ из выбранного подмножества помечаются отказавшими на весь
горизонт (`failures: [{satellite_id, start_s: 0, end_s: horizon_s}]`) —
`reference_geometry.py` и так уже трактует `active = launch_batch <=
launch_stage AND id not in failed`, так что это физически то же самое,
что «спутник ещё не запущен», просто позволяет выбрать ЛЮБОЕ
подмножество, а не только целую партию запуска.

## Критерий выбора (и тай-брейк)

Основной критерий — максимизация доступности худшего клиента. При
равенстве, в порядке приоритета:

1. меньше худший перерыв связи (`worst_max_outage_s`);
2. выше средняя доступность (`mean_availability`);
3. меньше суммарное число смен маршрута (`route_churn`);
4. меньше отклонение от сбалансированной по плоскостям структуры
   (разница между максимальным и минимальным числом активных спутников
   на плоскость) — предпочитает распределять спутники равномерно по
   плоскостям, а не концентрировать в одной;
5. id спутника — исключительно для детерминизма при полном совпадении
   всего вышеперечисленного.

## Главный честный вывод: состав важнее количества

Готовый сценарий `02_first_launch` (Stage 1 «как есть» — все 16 спутников
из ОДНОЙ плоскости P1, `design.launch_stage=1`) даёт worst-доступность
**12,64 %**. Жадно подобранный состав из 16 спутников, распределённых по
ВСЕМ ТРЁМ плоскостям (5+6+5), даёт **31,39 %** — почти в 2,5 раза больше,
той же ценой (16 аппаратов), без единого изменения RAAN/phase. Это
означает: если бы первая партия запуска была распределена по плоскостям
равномерно вместо запуска целой плоскости целиком, устойчивость связи на
Stage 1 была бы кардинально лучше. Для Stage 2 (32 спутника) разница
меньше (61,81 % готового `02_first_launch`-подобного состава против
64,31 % жадного) — на этом масштабе состав уже не так критичен, поскольку
2 из 3 плоскостей и так задействованы почти полностью.

## Refine-фаза (опционально)

`refine_budget > 0` запускает поверх выбранного состава ТОТ ЖЕ самый
exact-оптимизатор (`search.optimize()`/`evaluate_configuration()`), что и
`/optimizer` — RAAN/phase подбираются заново для уже выбранного
подмножества спутников. Никакого нового алгоритма — чистое переиспользование.

## Ограничения

- Жадный алгоритм — эвристика, не гарантирует глобальный оптимум для
  каждого N.
- «Лучший состав» здесь означает лучший НАЙДЕННЫЙ при равновероятном
  включении спутников по одному — не то же самое, что «любые случайные N
  спутников дают такой результат» (это была бы отдельная, более суровая
  метрика наихудшего случая — N‑к анализ отказа, а не выбор развёртывания).
- Полный проход по 48 спутникам — тяжёлая операция (~4-5 минут); API
  поддерживает `max_search_size`, чтобы явно ограничить его для быстрых
  проверок конкретных N (см. docs/api.md).
