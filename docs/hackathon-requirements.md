# Соответствие требованиям кейса

Кейс: **«Проектирование устойчивой спутниковой группировки»**
(КосмоХакатон 2026). Полный текст — в `case_materials/`:
«Постановка задачи», «Описание данных», «Критерии оценки». Ниже —
сопоставление функциональных требований постановки задачи с фактической
реализацией NORD-48. Обновлено после этапа Hybrid Deployment
Optimization/Final Hardening — большинство пунктов, отмеченных в ранних
версиях этого документа как «не реализовано в v0.1», с тех пор построены;
статусы ниже отражают текущее состояние, не историю.

## 1. Подготовка и изменение конфигурации

| Требование | Реализация | Статус |
| --- | --- | --- |
| Загрузка сценария из предоставленного набора | `GET /scenarios/examples`, `GET /scenarios/examples/{id}` | готово |
| Отображение состава группировки, плоскостей, наземных пунктов, параметров расчёта | панель «Конфигурация» во frontend | готово |
| Загрузка собственного сценария того же формата | `POST /scenarios/upload` + кнопка «Загрузить JSON» | готово |
| Выбор очереди запуска (launch_stage) в интерфейсе | редактор варианта (`variant-editor.tsx`) меняет `launch_stage` у любого сценария; Deployment Planner дополнительно подбирает САМ состав по числу спутников, а не только по готовой партии | готово |
| Изменение RAAN и фазирования плоскостей | редактор варианта — вручную по плоскости; Оптимизатор (`/optimizer`) — автоматический точный поиск | готово |
| Добавление периодов недоступности спутников через интерфейс | Failure Lab (`/`, «Failure Lab») — выбор любых спутников и интервала `[начало, конец)` из UI, без правки JSON; редактор варианта также позволяет добавлять/удалять записи `failures` | готово |
| Сохранение варианта и возврат к нему для сравнения | «Сохранить вариант» в редакторе → список сохранённых вариантов сессии → добавление прогона в Compare | готово |

## 2. Моделирование покрытия и сети

| Требование | Реализация | Статус |
| --- | --- | --- |
| Положения активных спутников на каждом шаге | `geometry.py` организаторов через адаптер, `GET /simulations/{run_id}/snapshot` | готово |
| Видимость наземных пунктов | учитывается в `snapshot.edges` и в диагностике (`NO_VISIBLE_SATELLITE`) | готово |
| Доступные межспутниковые связи | `snapshot.edges` (тип `isl`), отображаются на глобусе | готово |
| Просмотр состояния сети в выбранный момент времени | временная шкала + `snapshot?t_s=` | готово |
| Периоды отсутствия связи по пункту | `GET /simulations/{run_id}/timeline`, полоса доступности под шкалой | готово |

## 3. Маршрутизация и реакция на отказы

| Требование | Реализация | Статус |
| --- | --- | --- |
| Маршрут от наземного пункта до шлюза через спутниковую сеть | `GET /simulations/{run_id}/route` | готово |
| Пересчёт маршрута при изменении положения/доступности аппаратов | маршрут вычисляется заново на каждый шаг симуляции | готово |
| Причина отсутствия маршрута (нет видимого спутника / разрыв сети / нет контакта со шлюзом / его недоступность) | 4 категории диагностики — `NO_VISIBLE_SATELLITE`, `ISL_NETWORK_SPLIT`, `NO_GATEWAY_CONTACT`, `GATEWAY_OUTAGE` | готово |
| Свободный выбор способа поиска маршрута (команда сама решает) | реализованы 2 стратегии — минимум переходов (BFS) и минимальная длина (Дейкстра) | готово |

## 4. Сравнение вариантов и рекомендации

| Требование | Реализация | Статус |
| --- | --- | --- |
| Сопоставление минимум двух сохранённых вариантов | `/compare` — 2–10 завершённых расчётов относительно явного baseline | готово |
| Сравнение по доступности, перерывам, характеристикам маршрутов | `/compare` — по каждому клиенту, дельты от baseline, diff конфигурации | готово |
| Расчёт для полной группировки, промежуточного этапа и сценария отказов | все 4 исходных сценария считаются полностью и проходят регрессионные тесты; Deployment Planner дополнительно считает произвольные промежуточные составы | готово |
| *(доп.)* Автоматический подбор конфигурации | Оптимизатор (`/optimizer`) — exact RAAN/phase поиск (normal/robust/constrained_robust) + Deployment Planner (подбор состава) | готово |
| *(доп.)* Поиск наиболее уязвимых аппаратов | N-1 criticality (`/resilience`, «Критические аппараты») — полный ranking по всем активным спутникам | готово |
| *(доп.)* Анализ резервных путей | Route Redundancy (`/resilience`, «Резервирование») — есть ли независимый резервный путь помимо основного | готово |
| *(доп.)* Сравнение стратегий маршрутизации | Routing Analysis (`/resilience`, «Маршрутизация») — точное сравнение всех 4 стратегий на одном и том же горизонте | готово |

## Требования к интерфейсу

| Требование | Реализация | Статус |
| --- | --- | --- |

| Сброс изменений и повторный запуск | новый расчёт запускается кнопкой в любой момент; редактор варианта работает над копией сценария, исходный JSON не меняется | готово |

## Данные и расчётный модуль

Все 4 сценария из комплекта используются без изменений
(`data/scenarios/raw/`), `geometry.py` организаторов используется как
есть, без переписывания (`case_materials/calculation/geometry.py` →
`backend/app/calculation/geometry/reference_geometry.py`). Формат
выгрузки результата — `GET /simulations/{run_id}/export` (см.
[api.md](api.md)).
