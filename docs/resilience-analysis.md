# Анализ устойчивости

## Два разных режима

Страница `/resilience` решает пять связанных задач:

- **Monte Carlo** оценивает сетевую связность при K случайно отказавших на весь
  период аппаратах;
- **Маршрутизация** детерминированно оценивает качество выбранных путей при
  известной динамике сети: lifetime, margin, hops и перестроения.
- **Отказ** сравнивает baseline с временным derived failure overlay;
- **Критические аппараты** выполняет exhaustive N-1 без повторного расчёта
  geometry. Методика и результаты — в [failure-analysis.md](failure-analysis.md).
- **Порог отказоустойчивости** проверяет exact N-2 всех пар; методика и
  фактический результат — в [failure-threshold.md](failure-threshold.md).

Availability сохранена в прежнем определении. Она одинакова у полных
path-finding стратегий на одном графе и потому сама по себе не сравнивает
качество пути. Фактический анализ четырёх сценариев приведён в
[routing-experiments.md](routing-experiments.md).

Рекомендация Route Stability Analysis не использует score или ML. Применяется
лексикографический порядок: максимальная средняя availability по клиентам,
затем средняя median segment lifetime, затем средний P05 bottleneck margin,
затем меньше route changes и меньше mean hops. API возвращает обоснование с
фактическими значениями.

## Monte Carlo стресс-тест

## Что это и, главное, что это НЕ

`POST /api/v1/resilience/monte-carlo` — **синтетический стресс-тест**, не
оценка вероятности отказа. В исходных данных кейса нет вероятности отказа
отдельного спутника — есть только конечный список спутников и явные
периоды их недоступности (`failure_windows`) в некоторых сценариях. Смысл
инструмента — ответить на другой, поддержанный данными вопрос:

> Если ровно K аппаратов из развёрнутой группировки внезапно и
> одновременно откажут на весь расчётный горизонт — какие именно K,
> выбранные равновероятно случайно, сильнее всего повредят сети, и какая
> из трёх стратегий маршрутизации в среднем устойчивее к такому сценарию?

Это НЕ Монте-Карло по надёжности (нет речи о MTBF, интенсивности отказов
или байесовской оценке риска) — это перебор случайных **комбинаций**
одновременного отказа фиксированного числа аппаратов, с полным точным
пересчётом сети для каждой комбинации. Ни один шаг не приближённый и не
обучен на данных — только графовые алгоритмы, честно посчитанные заново.

## Точная семантика одного испытания

Одно испытание (`trial`):

1. Из аппаратов, доступных на этапе развёртывания сценария
   (`launch_batch <= design.launch_stage`), равновероятно и без повторов
   выбираются ровно `K = failed_satellites_count` штук
   (`numpy.random.default_rng(seed).choice(..., replace=False)`).
2. Эти K аппаратов считаются недоступными **весь** расчётный горизонт
   (все 720 шагов) — не в какой-то один момент и не с плановым
   восстановлением.
3. Для каждой запрошенной стратегии маршрутизации прогоняется **полный**
   расчёт: 720 шагов × все анализируемые клиенты, с построением графа,
   поиском маршрута и (при необходимости) диагностикой — тот же код, что
   и в обычном `POST /simulations/run`, без каких-либо упрощений.
4. Испытание повторяется `iterations` раз с одним и тем же `seed` —
   результат детерминирован и воспроизводим (см. `test_seed_reproducibility`
   в [`test_monte_carlo.py`](../backend/tests/integration/test_monte_carlo.py)).

Если `failed_satellites_count` больше числа доступных аппаратов, K
ограничивается их числом (`parameters.failed_satellites_count` в ответе
может быть меньше `parameters.requested_failed_satellites_count`).

## Быстродействие: что переиспользуется, а что — нет

Один прогон K=5, iterations=100, все 3 стратегии, `01_full_constellation`
(3 клиента) — это 100 испытаний × 3 стратегии × 3 клиента × 720 шагов =
**648 000** точных расчётов маршрута. Чтобы это оставалось быстрым без
потери точности:

- орбитальная геометрия (`reference_geometry.snapshot`) и граф контактов
  каждого из 720 шагов считаются **один раз** на весь эксперимент и
  переиспользуются во всех испытаниях — случайный отказ спутника не
  двигает орбиты и не меняет дальности/углы места других линий, он только
  убирает узлы из уже построенного графа;
- для каждого испытания граф с отказавшими узлами — **реальная копия**
  (`.copy()` + `.remove_nodes_from()`), не «представление» (`subgraph`
  view). Промежуточная попытка перейти на view ради экономии копирования
  была измерена и **отклонена** — она оказалась медленнее (64.2–62.6 с
  против 49.4–50.5 с на этом же прогоне), потому что маршрутизация делает
  много обращений к атрибутам каждого ребра, а у view это обращение
  дороже, чем у обычного графа; экономия на копировании не окупила эти
  накладные расходы. Корректность до/после этой правки была сверена
  побайтово (одинаковый `recommended_strategy`, все
  `all_clients_target_fraction`, все `mean` по клиентам,
  `worst_trial`) — оптимизация не изменила результат, только время.
- по каждому испытанию в память кладутся только агрегаты (счётчик
  доступных шагов, текущая и максимальная серия перерыва) — не полная
  запись маршрута на каждый шаг; полная диагностика причин перерывов
  пересчитывается заново только для двух «заголовочных» испытаний
  (`worst_trial`/`best_trial`), а не для всех `iterations`.

Измеренное время: K=5, iterations=100, 3 стратегии, `01_full_constellation`
— около 50 секунд. Это осознанный компромисс: инструмент запускается по
явному нажатию «Запустить стресс-тест», а не блокирует загрузку страницы,
и 648 000 точных расчётов быстрее считать честно, чем гадать, что можно
безопасно упростить.

## Метрики на выходе

По каждой (стратегии, клиенту) — за все `iterations` испытаний:
`mean`/`std`/`min`/`max`/`p05`/`p50`/`p95` доступности, доля испытаний,
где доступность клиента достигла целевой (`target_success_fraction`),
средний и P95 максимального перерыва.

По каждой стратегии — агрегат по ХУДШЕМУ клиенту каждого испытания:
`mean_worst_client_availability`, `p05_worst_client_availability` и доля
испытаний, где **все** клиенты одновременно достигли цели
(`all_clients_target_fraction`) — то есть насколько устойчива стратегия
не «в среднем по больнице», а в худшем для конкретного испытания случае.

## Правило выбора стратегии

Рекомендация — **не ML и не эвристика с настраиваемыми весами**, а
детерминированное каскадное правило по уже посчитанным цифрам, в порядке
приоритета:

1. выше `all_clients_target_fraction` (доля испытаний, где цель достигли
   ВСЕ клиенты);
2. при равенстве — выше `p05_worst_client_availability` (худший случай
   не в среднем, а в нижнем хвосте распределения);
3. при равенстве — выше `mean_worst_client_availability`;
4. при равенстве — предпочесть более простую стратегию
   (`minimum_hops` → `minimum_distance` → `maximum_margin`).

Реализация — `_recommend_strategy()` в
[`monte_carlo.py`](../backend/app/calculation/resilience/monte_carlo.py);
`recommended_reason` в ответе API — не статический текст, а собранная по
факту строка: она называет только те уровни каскада, до которых
действительно дошло сравнение (если стратегии разошлись на первом же
критерии, дальнейшие уровни в объяснении не упоминаются).

## Реальный результат экспериментов — и почему он именно такой

Ниже — фактические прогоны (не гипотеза «наперёд»), через
`POST /resilience/monte-carlo`, `01_full_constellation`, `seed=42`,
`iterations=100`, все три стратегии:

| K | Рекомендована | all_clients_target_fraction | P5 худшего клиента | mean худшего клиента |
| --- | --- | --- | --- | --- |
| 1 | `minimum_hops` | 100,0 % | 94,3 % | 94,7 % |
| 3 | `minimum_hops` | 91,0 % | 89,9 % | 90,6 % |
| 5 | `minimum_hops` | 0,0 % | 85,3 % | 86,1 % |
| 10 | `minimum_hops` | 0,0 % | 72,6 % | 74,0 % |

Дополнительно проверено на другом сценарии (`04_link_range`, ISL
ограничен 2000 км, K=5, iterations=50, seed=42) — та же картина.

**Честный результат: во всех прогонах все три стратегии дают ЧИСЛЕННО
ИДЕНТИЧНЫЕ показатели доступности** (`mean`, `p05`, `p50`, `p95`,
`target_success_fraction` — совпадают у `minimum_hops`,
`minimum_distance` и `maximum_margin` вплоть до дробной доли процента),
поэтому во всех случаях рекомендация доходит до 4-го уровня каскада и
побеждает `minimum_hops` как более простая стратегия. Это **не
совпадение и не ошибка**, а прямое следствие того, что именно измеряет
доступность:

`availability` в этом проекте — булево «нашёлся ли путь клиент → …→
шлюз» на шаге времени, а не качество этого пути. Если граф связности
между клиентом и шлюзом СВЯЗЕН, то путь найдут абсолютно все три
алгоритма (BFS, Дейкстра, widest-path) — они различаются только тем,
КАКОЙ из существующих путей выберут, а не тем, существует ли путь
вообще. Случайный отказ K спутников либо разрывает эту связность, либо
нет — независимо от того, какой стратегией её потом обходят. Поэтому
Monte Carlo-метрика «доступность» в этом сценарии принципиально не может
различить стратегии маршрутизации — все три обязаны находить путь при
одном и том же графе, если он существует.

Выигрыш `maximum_margin` — не в том, находится ли путь, а в том,
НАСКОЛЬКО ЗАПАС у найденного пути (устойчивость к дальнейшей деградации
конкретной линии, не к отказу целого спутника). Это видно не в агрегатах
Monte Carlo, а в поле `bottleneck_margin` отдельного маршрута: например,
на `04_link_range`, `C70`, `t_s=21600`, `minimum_hops` выбирает путь
`C70→S09→G_MUR` с запасом узкого места 1,14 %, а `maximum_margin` для
того же клиента и момента — путь `C70→S25→S09→G_MUR` (на один переход
длиннее) с запасом 1,60 % — жертвует одним переходом ради более
устойчивого канала. Monte Carlo, как он сейчас посчитан (по
`availability`), эту разницу не видит и не должен — это два разных
вопроса: «найдётся ли путь при потере K спутников» и «насколько выбранный
путь далёк от потери отдельной линии связи».

**Вывод без предрешённого победителя**: по критерию «стресс-тест
случайного отказа K спутников» рекомендуется `minimum_hops` — простейшая
стратегия — потому что в данной модели измерения (`availability`) она
объективно не хуже двух остальных, а не потому, что `maximum_margin`
работает плохо. `maximum_margin` следует выбирать, когда важна не только
связность, но и запас конкретной линии на конкретный момент — это другая
задача, для которой в проекте есть отдельный, уже посчитанный показатель
(`bottleneck_margin`/`bottleneck_edge` в ответе `GET .../route`), а не
Monte Carlo.

## Худший случай (`worst_trial`/`best_trial`)

Среди всех `iterations` испытаний, по показателю худшего клиента
рекомендованной стратегии, выбираются испытание с минимальной и с
максимальной доступностью худшего клиента. Для них дополнительно (и
только для них — не для всех испытаний) пересчитывается разбивка причин
перерывов связи (`diagnostic_breakdown`) через
`app/calculation/diagnostics/diagnostics.py`.

## Ограничения

- Не учитывает вероятность или время до отказа — только факт «K
  аппаратов отказали и не восстановятся» на весь горизонт.
- Отказы аппаратов равновероятны и независимы (простая случайная выборка
  без повторов) — нет модели корреляции отказов (например, одна орбитальная
  плоскость целиком).
- Как показано выше, при доступности как единственной метрике три
  стратегии маршрутизации неотличимы в этом эксперименте — сравнение
  «какая стратегия устойчивее по запасу линии в среднем по случайным
  отказам» этот эндпоинт не считает (это отдельная, не заказанная в этом
  этапе задача).
- `iterations` ограничено 1000 (`MAX_ITERATIONS`) — защита от случайного
  многочасового запроса.
