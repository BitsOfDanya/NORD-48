# Отчёт по этапу: Design Decision & Economics + Hybrid Deployment Optimization + Threshold Verification + Resilience/Redundancy Metrics + Frontend Polish

Дата: 2026-09-12. Команда «5bit», КосмоХакатон 2026, проект NORD-48.

## 1. Резюме

Этап добавляет пять новых аналитических возможностей поверх существующей
базы (Simulation / Compare / Summary / Failure Lab / Monte Carlo / Routing
Analysis / N-1 / N-2 / Optimizer / Deployment Planner) и связывает их
сквозным фронтендом. Ничего из перечисленного не сломано — см. §14
(регрессия) и §17 (тесты).

Новое:

1. **Hybrid Deployment Optimization** — оркестрация «состав → RAAN/phase →
   ревалидация» поверх уже существующих алгоритмов (без нового решателя).
2. **Threshold Verification** — независимая (swap-refinement) проверка
   порога N=40-45, НЕ полный перебор.
3. **Route Redundancy** — три раздельных процента на клиента (есть
   резерв / единственный путь / маршрута нет).
4. **ISL Sensitivity** — точный sweep минимальной дальности ISL для target.
5. **Cost/Economics layer** — resource-only по умолчанию, opt-in cost mode
   без единого зашитого коэффициента цены.
6. **Acceptance Matrix 2.0** — новые столбцы (запас до target, резерв
   пути, требуемый ISL, число спутников/пусков, оценка стоимости).
7. **Frontend**: 5 новых панелей, 3 новые вкладки Optimizer, 1 новая
   вкладка Resilience, всё через существующие CSS-токены и компоненты
   (Card/Button/Select/Tabs) — без визуального редизайна с нуля.

## 2. Hybrid Deployment Optimization

`docs/deployment-optimization.md`. Три шага, все — переиспользование
существующего кода:

1. `greedy_sequence()` — состав (какие спутники).
2. `refine_stage()` — тот же exact-оптимизатор `/optimizer`, суженный на
   выбранный состав.
3. `evaluate_subset()` — точная ревалидация финальной конфигурации.

**Nested Deployment Sequence** — Stage1(16) ⊂ Stage2(32) ⊂ Stage3(48)
гарантированно по построению (одна непрерывная последовательность
жадного наращивания), отдельный алгоритм вложенности не потребовался —
только документирование свойства.

## 3. Threshold Verification (N=40-45) — ключевой результат сессии

`docs/design-threshold-verification.md`. Метод: **swap refinement**
(steepest-descent обмен активный↔неактивный спутник, до 3 проходов) поверх
жадного состава каждого N — независимая от порядка добавления проверка,
НЕ `C(48,N)` перебор.

Фоновый прогон (`01_full_constellation`, `minimum_hops`, target ≥90%):
построение полной последовательности 1..48 — **262,4 с**; уточнение
N=40..45 — **1664,6 с** (≈32 мин суммарно).

| N | Жадный worst | После swap-refinement | Обменов | Target |
| --- | --- | --- | --- | --- |
| 40 | 81,39 % | 82,64 % | 3 | FAIL |
| 41 | 83,47 % | 84,72 % | 3 | FAIL |
| 42 | 85,56 % | 86,53 % | 3 | FAIL |
| 43 | 87,64 % | 88,33 % | 2 | FAIL |
| **44** | 89,72 % | **90,14 %** | 2 | **PASS** |
| 45 | 91,53 % | 91,94 % | 3 | PASS |

**Первый найденный размер, достигающий target: N = 44** (обмены `S40→S38`,
`S39→S20`) — на единицу меньше, чем греди-only порог (N=45). Это НЕ
математически доказанный минимум — формулировка везде в UI/докладе:
«первый найденный размер, достигающий target» / «минимальный размер,
найденный текущим поиском».

## 4. Resilience Reserve — устойчивость к N-1 у граничных кандидатов

Дополнительно проверено (не входило в исходный swap-refinement прогон,
досчитано отдельно после получения результатов §3):

| N | Worst (штатный) | Худший N-1 drop | Worst после N-1 | Нарушений |
| --- | --- | --- | --- | --- |
| 44 (refined) | 90,14 % | −3,33 п.п. | ≈86,81 % | 3 |
| 45 (refined) | 91,94 % | −3,33 п.п. | ≈88,61 % | 1 |
| 46 (жадный) | 93,33 % | −3,33 п.п. | **≈90,00 %** | **0** |

**N=44 — минимум для штатного режима, но с нулевым запасом на отказ
одного спутника.** N=46 — первый найденный размер, сохраняющий target
даже после худшего единичного отказа.

## 5. Route Redundancy

`docs/network-redundancy.md`. Для каждого (клиент, шаг) с маршрутом:
промежуточные спутники основного пути удаляются, ищется независимый
резерв. Три раздельных процента, НЕ единая свёрнутая метрика.

Реальные результаты (`01_full_constellation`, все 48 спутников):

| Клиент | Есть резерв | Единственный путь | Маршрута нет |
| --- | --- | --- | --- |
| C65 | 16,5 % | 80,1 % | 3,3 % |
| C70 | 30,6 % | 68,2 % | 1,3 % |
| C72 | 37,2 % | 61,7 % | 1,1 % |

На кандидате N=44 (после swap-refinement) резерв заметно ниже (C65: 11,8%,
C70: 22,5%, C72: 25,7%) — ожидаемо: меньше спутников-ретрансляторов на
выбор при том же покрытии.

## 6. ISL Sensitivity

`docs/isl-sensitivity.md`. Точный sweep (не аппроксимация) +
опциональное уточнение границы с шагом 50 км.

- Полная группировка (48 спутников): минимальная дальность ISL для target
  ≥90% — **2750 км**.
- Кандидат N=44 (после swap-refinement): минимальная дальность ISL —
  **тоже 2750 км** — сужение состава до 44 спутников не потребовало более
  длинной линии связи.

## 7. Cost / Economics Layer

`docs/cost-effectiveness.md`, `docs/cost-sources.md` (последний уже
существовал на момент начала этапа — 4 реальных источника: Sitronics
дек. 2021, Интерфакс 2022 про 157-спутниковый проект (~20 млрд ₽ —
явно ПРОЕКТНАЯ стоимость, не цена за спутник), Коммерсантъ 2019 про
Главкосмос rideshare, ГТЛК/СПУТНИКС лизинг без публичной цены).

Два режима:

- **Resource-only** (по умолчанию) — только количество спутников/пусков,
  без единого рубля.
- **Cost mode** (opt-in) — активируется, только если пользователь ЯВНО
  задал `satellite_unit_cost_rub`; иначе `estimate_cost()` возвращает
  `None`. Историческая оценка (Sitronics) доступна как кнопка-пресет во
  фронтенде с явной пометкой источника/даты/оговорки, никогда не
  применяется тихо. Проверено в браузере: 48 спутников × 10 млн ₽ + 48
  пусков × 10 млн ₽ = **960 000 000 ₽** (при вместимости пуска = 1 спутник,
  как в исторической оценке).

Cost-effectiveness метрики: `cost_per_availability_point`,
`incremental_cost_per_pp`, `estimated_cost_delta` — простые отношения, не
свёрнутый рейтинг.

## 9. Дизайн-рекомендация (единая, без произвольного взвешенного score)

Following the mandatory gate structure (NORMAL target ≥90% сначала, затем
resilience/backup-path/outage/cost прозрачно, без свёртки в один «рейтинг»):

- **Если приоритет — минимальное число спутников на штатный режим**:
  **N=44** (жадный состав + 2 обмена: `S40→S38`, `S39→S20`), worst=90,14%.
  Оговорка: нулевой запас на N-1 (см. §4) — при отказе ЛЮБОГО одного из
  наиболее критичных спутников (S10/S34) target нарушается у 3 клиентов.
- **Если приоритет — устойчивость к единичному отказу спутника**:
  **N=46** (жадный состав, без уточнения обменами), worst=93,33%,
  сохраняет target ≥90% даже после худшего N-1 (0 нарушений). Стоимость:
  +2 спутника относительно N=44 — при исторической оценке ≈40 млн ₽
  (2 × (10 млн ₽ производство + 10 млн ₽ пуск)).
- ISL-требование одинаково для обоих (2750 км) — не является
  дифференцирующим фактором между N=44 и N=46.
- Route redundancy заметно ниже 48-спутниковой полной группировки в обоих
  случаях — компромисс между экономией спутников и резервированием путей
  явный, не скрытый.

Итоговое решение (44 против 46, и любая денежная оценка) оставлено за
пользователем — инструмент показывает числа прозрачно, не выдаёт
единственный «правильный» ответ.

## 15. Что НЕ было сделано в этой сессии (честно, без замалчивания)

- **Полный визуальный редизайн** (Части 39-57 исходного ТЗ) — НЕ
  выполнен как отдельная масштабная работа. Новые панели используют уже
  существующие компоненты (`Card`, `Button`, `Select`, `Tabs`) и токены
  темы без изменений — то есть визуально консистентны с остальным
  приложением, но целенаправленный проход «layered workspace background /
  softer borders / compact metric cards» поверх уже существующих страниц
  не производился отдельно. Риск: субъективно, дизайн мог не получить
  описанного в ТЗ отдельного полишинга сверх органичного повторного
  использования существующих паттернов.
- **Множественные детерминированные старты / beam search** для threshold
  verification — не реализованы; использован один старт (жадный состав) +
  swap-refinement с `max_passes=3`. Указано явно в
  docs/design-threshold-verification.md как ограничение.
- **outagesWorstPercent/isl2000WorstPercent для кандидатов N=44/N=46** в
  Acceptance Matrix — не досчитаны (потребовало бы запуска этих
  кандидатов под стресс-профилями `03_satellite_outages`/`04_link_range`,
  что не было сделано, чтобы не указывать в таблице непроверенные числа).
  Столбцы новых метрик (запас/резерв/ISL) для этих кандидатов
  задокументированы отдельно в §3-§6 этого отчёта и в
  docs/design-threshold-verification.md, но НЕ внесены как отдельные
  строки Acceptance Matrix — во избежание неполных/частично «—» строк.
- Outage Quality metrics (`outage_quality.py`) — модуль и тесты написаны
  и проходят, но НЕ подключены к какой-либо новой UI-панели в этой
  сессии (только backend-слой).
